# Official CLI workers in Kemiri

Research snapshot: 19 November 2026 UTC. No product code changed. Google account access and model replies were not tested.

**Recommendation: do not use the owner’s consumer Antigravity subscription for Kemiri workers.** Google distinguishes a person directly prompting the official ACP agent from another agent delegating to it, even with human approval. For a worker, use approved API/enterprise billing and let the official agent run the whole task. For native Kemiri features, use a direct pi-ai API provider. For subscription use, run `agy` directly or consider a separately approved, single-user interactive ACP client with no delegation. See [How T3 Code does it](#how-t3-code-does-it).

## What Google ships

- **Google Antigravity CLI** is the native Go terminal agent, executable **`agy`**, not the `@google/gemini-cli` npm package and not the Python SDK. On Linux use Google’s [quickstart](https://antigravity.google/docs/getting-started/) installer, `curl -fsSL https://antigravity.google/cli/install.sh | bash`. For evaluation, fetch and inspect the [script](https://antigravity.google/cli/install.sh) first. The script selects an architecture from a Google release manifest, verifies the download against SHA-512, and installs `agy` to `~/.local/bin` by default (`--dir` overrides it). The installed Linux x86-64 build reported **1.5.12**, matching the [November 19 release](https://github.com/google-antigravity/antigravity-cli/releases/tag/1.5.12). The live script rejected `--skip-path`, despite [authentication docs](https://antigravity.google/docs/install/) listing it and `--skip-aliases`. Use an isolated HOME rather than assuming those flags work.
- The CLI is the terminal surface of the [Antigravity platform](https://antigravity.google/docs/overview/), and shares its agent engine with the standalone Antigravity App (formerly Agent Manager, launched as Antigravity 2.0). The **Antigravity IDE** is the separate full editor; it is not required to install or run `agy`. Google also documents editor integrations that run `agy acp`. The CLI is an agent with its own tools and session history, not a raw Gemini endpoint.
- **Gemini CLI** is a separate tool. Per Google’s [transition notice](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/), requests on Gemini CLI stopped on June 18, 2026 for Google AI Pro/Ultra and free Gemini Code Assist for individuals. The notice preserves Gemini Code Assist Standard/Enterprise access and paid Gemini/Gemini Enterprise Agent Platform API-key access. The [migration guide](https://antigravity.google/docs/cli/gcli-migration/) covers importing extensions as plugins and moving skills/MCP configuration. Do not use Gemini CLI as a fallback for consumer quota.

### Plans and models

The [model matrix](https://antigravity.google/docs/models/) is more specific than the [plans overview](https://antigravity.google/docs/plans/). This is the documented lineup, not an account entitlement test. Check `agy models` or interactive `/model` on the authorized account. Do not hard-code slugs or assume Gemini API billing offers the subscription catalog.

| Google AI Pro paid | Gemini 3.8 Flash, Gemini 4 Neon, Argon and Hydrogen, Orchestrator (Neon/Argon), Claude Sonnet 5.5 (thinking) and Opus 5.5 (thinking). Five-hour baseline refresh until the weekly limit. |

## Program interface and observed results

| Need | Official interface |
| --- | --- |
| One task | [`agy -p "prompt"`](https://antigravity.google/docs/cli/headless/) (`--print` or `--prompt`). One full agent turn, potentially many model calls and tool actions. `--model`, `--effort` and `--agent` select settings. An invalid pinned model fails in headless mode rather than silently falling back. |
| Prompts on stdin | Use `agy --input-format stream-json --output-format stream-json` and send one line like `{"event":"user","message":{"content":"Reply with PING."}}`. String or text blocks only. Keep the pipe open for sequential turns, read one result per turn and close stdin to finish. Do not pass `-p` with a prompt in this mode. A bare `-p` reading a plain text pipe did not work in the test. |
| Events and results | `--output-format text`, `json` (one envelope) or `stream-json` (NDJSON `init`, `step_update`, `result`). Stdout is data; stderr carries diagnostics. Events can contain text deltas, tool calls and results, subagent info and token counters. `--json-schema` constrains the final result, not the whole stream. Inspect exit code **and** terminal status; exit 0 only means a response, not that the requested edits or tests happened. |
| Session and cwd | Start in the intended working directory (`cwd` on spawn), not a global `chdir`. `--add-dir` adds workspace directories and `--project` selects a known project. Save `conversation_id`, resume with `--conversation ID` in the same profile/workspace; avoid `--continue` in a worker pool because it picks the most recent conversation. A CLI conversation ID is not permission to retry a turn with side effects. |
| Tools and approvals | [`--mode plan`, `accept-edits`, `auto`, `--sandbox`, and per-run `--settings`](https://antigravity.google/docs/cli/reference), plus scoped `permissions.allow`/deny rules in `~/.gemini/antigravity-cli/settings.json`. Headless uses configured policy and soft-denies actions requiring unavailable approval; it can still exit 0. Do not use `--dangerously-skip-permissions` for a Kemiri worker. `--disable-slash-commands` disables slash/skill expansion in print mode, not all tools. Use both CLI policy and OS workspace isolation. |
| Agent protocol | [`agy acp`](https://antigravity.google/docs/cli/acp/) is an official ACP stdio server (JSON-RPC), with approval callbacks, working directory, and load/resume/list/close support in the [editor guide](https://antigravity.google/docs/ide/extensions/acp/). Authenticate once via `agy` or `agy acp --login`. The guide has an “Any ACP client” section and documents `--process-per-session` for editor-configured HTTP MCP. Verify capabilities during initialization rather than assuming all clients expose them. |
| Tool protocol | [`agy mcp`](https://antigravity.google/docs/mcp/#antigravity-cli) **manages MCP servers the CLI consumes** (add/remove/list/enable/disable), not an MCP server exposing the agent itself. CLI supports local stdio and remote configurations; use `~/.gemini/config/mcp_config.json` or `.agents/mcp_config.json` at workspace level. ACP and MCP solve different problems. |
| SDK | The official [Antigravity SDK](https://antigravity.google/docs/sdk/overview/) is the separate Python 3.10+ package `google-antigravity`. It runs an agent with state, streaming, custom tools, policies, hooks and MCP. The [SDK auth section](https://antigravity.google/docs/install/#programmatic-authentication) documents Gemini API keys, Gemini Enterprise/Vertex/ADC and local models. It does not document programmatic use of a consumer subscription. |

**Observed on Linux x86-64:** The official script verified and installed 1.5.12 in an empty temporary HOME with isolated XDG directories, no inherited credential variables and an empty working directory. `agy --version`, `agy --help`, `agy acp --help`, and `agy mcp --help` ran. With no sign-in, the `-p` flag probe printed an auth-related diagnostic and hit the external deadline, even with stdin closed and in a detached session; Google’s headless docs say such a run should exit with an auth error. The documented NDJSON stdin probe exited **1** with an auth diagnostic. The bare `-p` plus plain pipe exited **2**. No reply was produced. No consent URLs, codes, tokens, or raw auth output were retained. Temp homes and installer files were removed. These checks do not verify authenticated streaming, permissions, resume, MCP calls, ACP handshake, account entitlement or refresh.

**What needs the owner:** For direct subscription use, the owner signs into `agy` personally, then runs `agy models` and, if desired, a direct one-off `agy -p` prompt outside Kemiri. [Google’s auth guide](https://antigravity.google/docs/install/) documents browser sign-in and an SSH flow where the owner opens a URL locally and pastes the authorization code into the remote terminal. Keep both out of Kemiri and task reports. Google documents reusing the CLI’s cached credentials and Linux Secret Service/keyring. It does not prove persistence across service restarts on the intended server. Validate with the approved test identity after logout/expiry and service restart. Treat missing keyring access, revoked consent, MFA and refresh failures as “sign-in needed,” not a retry loop. For API-billed `agy` use Google AI Studio `GEMINI_API_KEY` with `modelProvider: "gemini"`; for enterprise automation Google documents `AGY_ADC_AUTH=true` and Cloud ADC. Neither spends the consumer subscription. The [1.5.12 release notes](https://github.com/google-antigravity/antigravity-cli/releases/tag/1.5.12) also say API-key mode does not support Remote Control or remote agents.

## Google’s rules and real enforcement

[Google Antigravity Additional Terms of Service](https://antigravity.google/terms/), clause 6:

> You must not abuse, harm, interfere with, or disrupt the Service. This includes, but is not limited to, using the Service in connection with products not provided by us. Using third party software, tools, or services to access the Service (e.g. using OpenClaw with Antigravity OAuth) is a breach of this Agreement. Such actions may be grounds for suspension or termination of your Antigravity and/or Gemini CLI accounts.

[Google’s FAQ, “Can I use Antigravity CLI headless mode in third-party coding agents or automate account switching?”](https://antigravity.google/docs/faq/#can-i-use-antigravity-cli-headless-mode-in-third-party-coding-agents-or-automate-account-switching):

> Antigravity CLI headless mode (agy -p) is intended for direct scripting and CI workflows. Wrapping agy inside third-party coding agents or applications, or automating account rotation, is not supported under consumer plans.

In the same FAQ Google says, “To use a third-party coding agent with Gemini, we recommend using a Gemini Enterprise or Google AI Studio API key.” Google also documents subprocess-based editor integration through ACP, including non-Google editors. [Google’s forum guidance on delegation](https://discuss.ai.google.dev/t/200697/2) says ACP does not make consumer-plan delegation supported, even when a human approves each subtask. Ask Google for written confirmation before offering any separate interactive consumer mode in Kemiri. For enterprise use, confirm the organization’s terms and approval for the specific setup. See the [Gemini API terms](https://ai.google.dev/gemini-api/terms) for the separate API route.

**Enforcement:** In [Google’s Gemini CLI announcement on bans and reinstatement](https://github.com/google-gemini/gemini-cli/discussions/20632), the team said: “These were the result of a series of Antigravity bans rolled out to address violations of the Antigravity Terms of Service (ToS), specifically the use of 3rd party tools or proxies to access Antigravity resources and quotas.” That announcement discussed restoring affected users, not permission to resume the behavior. A [paid Ultra user reported sudden restrictions after OpenClaw OAuth](https://discuss.ai.google.dev/t/account-restricted-without-warning-google-ai-ultra-oauth-via-openclaw/122778); [another paid user reported a 403 after using OpenClaw](https://discuss.ai.google.dev/t/urgent-mass-403-tos-bans-on-gemini-api-antigravity-for-open-source-cli-users-paid-tier/124508). These are self-reports of third-party access, not proof that Google banned a wrapper using only the stock `agy` binary. No such verified case was found in this review. The current FAQ, not an extrapolation from those cases, is the reason to avoid the wrapper. Do not extract OAuth, send it through pi-ai, impersonate the CLI, or rotate accounts to extend quota.

## How T3 Code does it

**Snapshot:** 19 November 2026, [`pingdotgg/t3code`](https://github.com/pingdotgg/t3code) at [`bc606280`](https://github.com/pingdotgg/t3code/commit/bc6062805db775019cf6f13cc543e694ad9e20fc), with [release notes](https://github.com/pingdotgg/t3code/releases) checked separately. This is Theo Browne and Julius Marminge’s MIT-licensed [T3 Code](https://t3.codes/), not a model API or a replacement agent loop. Its server starts or connects to agents on the selected machine, stores thread state, and sends updates to web, desktop and phone clients. This was source and documentation research, not a signed-in runtime test.

**Available vs. planned.** The [built-in driver list][t3-drivers] contains Codex, Claude Code, Cursor, Grok Build, OpenCode, Antigravity, Kiro, Pi, Muse Code and fx, plus the generic ACP driver. Kiro shipped as Early Access in [v0.1.7](https://github.com/pingdotgg/t3code/releases/tag/v0.1.7). The [ACP setup guide][t3-acp] supports both Registry entries (e.g. Copilot, Devin and Gemini CLI) and local ACP executables. Gemini CLI is **available through ACP, not a dedicated driver or just a plan**: the [T3 discussion](https://github.com/pingdotgg/t3code/discussions/6687) points to the merged integration, and the [live registry](https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json) listed `@google/gemini-cli@0.69.0` with `--acp`. This does not restore consumer entitlement lost in Google’s June transition; use an eligible Code Assist Standard/Enterprise or API credential, per the transition notice above. No current maintainer commitment to a dedicated Gemini CLI adapter or additional named built-in was found; old “coming soon” labels and open proposals are not a roadmap.

| Agent | How the T3 server drives it |
| --- | --- |
| **Codex** | Starts `codex app-server` over stdio JSON-RPC, sharing one process across threads of an instance. Initializes the connection, maps T3 threads to native `thread/start` or `thread/resume` IDs, and uses `turn/start`, `turn/steer` and `turn/interrupt`. Codex runs tools and sandbox policy; server approval RPCs for commands, edits and permissions become T3 requests. Item/delta notifications stream output; `thread/tokenUsage/updated` reports live token counts. See [`CodexAdapterV2.ts`][t3-codex] and [OpenAI’s App Server docs](https://developers.openai.com/codex/app-server/). |
| **Claude Code** | Uses `@anthropic-ai/claude-agent-sdk` `query()` with streaming prompt input, the configured Claude executable, and the project cwd. SDK manages the child protocol; T3 does not parse a PTY. It keeps native session IDs and resumes through SDK `resume`, maps `canUseTool` and questions to pending responses, and feeds MCP to Claude’s own tool loop. With `includePartialMessages`, T3 streams text, reasoning and tool events, uses SDK interrupt, and reads per-message and final-result usage. See [`ClaudeAdapterV2.ts`][t3-claude]. |
| **Antigravity** | The native installation starts `agy acp` with a per-instance profile and project cwd; the code also supports the older standalone `agy_acp_server` plus its Google harness. T3 follows Google’s CLI release channel and checks SHA-512 for the managed native archive; a compatible manual `agy` path works too. The shared ACP runtime initializes/authenticates, creates or resumes/loads sessions by opaque ID, sends `session/prompt`, receives streamed text/thought/tool updates and relays native permission choices, then uses `session/cancel` for Stop. The agent runs tools/MCP; negotiated client file reads are scoped. T3 uses ACP usage where emitted and reads local Antigravity conversation databases for history. It cannot natively rewind the agent conversation or compact over this adapter. See [`AntigravityInstallation.ts`][t3-agy-install], [`antigravityAuthSupport.ts`][t3-agy-profile] and [`AntigravityAdapterV2.ts`][t3-agy]. |
| **Gemini CLI, Grok Build, Kiro, fx, and other ACP agents** | Generic Registry/local commands share the [ACP stdio runtime][t3-acp-runtime] and [event/permission adapter][t3-acp-adapter]. T3 negotiates ACP v2 preview or v1, only uses advertised load/resume/config capabilities, streams `session/update`, handles `session/request_permission` and client capabilities, and sends `session/cancel`. Auth comes from the agent, either its existing store or its advertised browser/terminal flow. Context/usage is optional. Dedicated flavors launch [`grok agent stdio`][t3-grok], [`kiro-cli acp`][t3-kiro], and [`fx acp`][t3-fx] with their own policy and cancellation differences; Grok Stop can restart the process group. |
| **Cursor** | Current [`CursorAgentSdk.ts`][t3-cursor] uses Cursor’s local TypeScript SDK (`@cursor/sdk`), not a `cursor-agent` terminal transcript. It creates/resumes native agent IDs with local cwd and sandbox options, streams run deltas, translates approval/input callbacks, and cancels native runs. T3 can use Cursor account login or an API key, and obtains account usage separately. |
| **OpenCode** | Launches `opencode serve` on a local port or connects to a configured server. The adapters use OpenCode’s HTTP API and event stream for native session IDs, prompt, tool/permission events and abort. V1 isolates chat servers per thread; v2 shares one server per instance with thread-scoped MCP and permission rules. Token totals come from native messages and stored history. See [the v1 and v2 ownership notes][t3-provider-rules] and [`OpenCodeRuntime.ts`][t3-opencode]. |
| **Pi and Muse Code** | [Pi’s adapter][t3-pi] uses the installed `pi --mode rpc` JSON-lines protocol, session files, extension UI replies, `abort` and session stats, with a namespaced T3 MCP bridge. [Muse’s adapter][t3-muse] uses Meta’s MSP stdio connection to `muse serve`, native `session/start` and `session/resume`, streamed item deltas, `approval/decide`, `turn/interrupt` and `session/tokenUsage`. Both keep agent-owned tool execution and native usage history. |

These are structured agent transports, not simulated typing or scraping a terminal screen. PTYs are separate: for shells, some sign-ins or terminal capabilities an ACP agent requests. T3’s [permission modes][t3-permissions] map to native policy, with supervised prompts or turn-time approvals where supported; the same UI label does not mean identical enforcement. [Usage][t3-usage] combines live counters, transcript readers and provider-specific account limits, not model API intercepts. Its API-equivalent prices are estimates, and T3 does not infer missing tokens from chat text.

**Who owns login and what vendors say.** Most integrations use an installed executable or vendor SDK on the server host with an existing provider login or an explicit API credential. Two important exceptions to “just reuse the terminal login”:

- **Codex:** T3 supports existing `codex login` and a separate managed **Connect with ChatGPT** flow that installs Codex and gets consent to share eligible plan usage. Its [managed auth code][t3-codex-auth] and [setup guide][t3-codex-doc] distinguish those routes. OpenAI [lists T3 as an open-source integration](https://learn.chatgpt.com/docs/sign-in-with-chatgpt#which-apps-support-sign-in-with-chatgpt) and [documents app-server with scoped plan-sharing OAuth](https://developers.openai.com/siwc/token-sharing-open-source). That is evidence for this specific route, not permission to reuse a CLI login in a hosted service.
- **Antigravity:** T3 has a separate native browser login (`oauth-personal`) in an isolated profile; the Google process exchanges/stores credentials, not T3’s model client. T3 can relay the loopback callback to the initiating flow on a remote host, strips ambient Google credentials and offers Gemini Enterprise, Gemini API-key and Agent Platform/Vertex modes. The [T3 setup guide][t3-agy-doc] says the runtime supplies account access and models, including partner models when offered; the forum guidance for general third-party consumer ACP clients says Gemini models in the plan, so do not promise partner-model access in Kemiri.
- **Claude:** T3 uses the native Claude Code login via the SDK. Anthropic [says plan-signed-in SDK use still draws from subscription limits](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), but its [developer policy](https://code.claude.com/docs/en/legal-and-compliance) directs products to API credentials and disallows offering Claude.ai login or routing plan credentials on users’ behalf. T3’s claim about its own integration does not grant Kemiri a subscription route. Theo [reported a small number of Anthropic bans](https://x.com/theo/status/2045618854932734260), said his contacts suspected error and could not reproduce them. That is evidence of reports, not confirmed causation or a blanket approval or objection by Anthropic.

T3’s [FAQ][t3-faq] says no bans, claims compliance with Codex, Claude Code and Google Antigravity terms, and links a claimed [SpaceXAI collaboration](https://x.com/SpaceXSI/status/2070195830192320600) for Grok Build and Cursor. Theo also [reported an informal Google assurance](https://x.com/theo/status/2095450015015788963). Stronger, but narrower: replies on Google’s developer forum distinguish [direct, single-user interactive T3/Zed use](https://discuss.ai.google.dev/t/197131/3) and [a private interactive `agy acp` client](https://discuss.ai.google.dev/t/198889/2) from [agent-to-agent delegation even with human approval](https://discuss.ai.google.dev/t/200697/2) and [queues or unattended use](https://discuss.ai.google.dev/t/197826/2). The replies are product guidance on Google’s forum, not a signed exception, and the accounts are not marked forum staff. The November 16 reply names T3 Code as a supported example **when the human directly prompts Antigravity**, but warns of suspension for delegation over either ACP or `agy -p` on a consumer plan. Approval clicks are not direct prompting. Google describes enforcement as loss of Antigravity and/or Gemini CLI access, not a blanket Google-account ban. No credible public report found linked a Google or Codex ban to ordinary T3 Code use; that is not proof of zero risk. Google’s documented proxy bans are a different case.

**What to copy.** Copy the [adapter boundary][t3-interface] and [driver rules][t3-driver-rules], not a vendor login or T3’s account policy. Give each configured backend an instance ID, approved billing profile, workspace and optional native session ref. Keep process admission, event normalization and explicit capabilities in the adapter, with separate usage sources and a deny-by-default approval policy. Kemiri owns scheduling, board state, artifact validation and final reports; the external worker owns its turn and tools. Stop with the native cancel operation first, bound teardown, settle outstanding approvals and don’t silently retry a partly executed turn. Use sanitized replay fixtures before a gated live pilot. Start with a single API/Cloud-billed Google worker on an approved route; use ACP if approvals or native resume are needed and headless NDJSON if a bounded task is enough. The same interface can later host Codex, Claude or other official agents with their own policy gates. If the owner only wants to use the subscription in a UI, consider a separate, directly human-prompted ACP mode after written confirmation for Kemiri, with no coordinator access, queue or scheduled runs.

## Where it would fit in Kemiri

- `packages/server/src/models.ts` builds `createModels({ credentials })` and calls `models.setProvider(...)` for OpenCode Go, Anthropic, OpenAI and OpenAI Codex. The installed pi-ai 1.5.2 `dist/models.d.ts` and `dist/types.d.ts` expose a `Provider` with auth, catalog and stream functions, and `Models.streamSimple()` handles native assistant content/tool calls and usage. The provider gets a normalized transcript carrying system instructions and tool schemas. Returning arbitrary text that happens to describe a tool call is not the same contract. A provider entry also needs catalog/settings/auth integration. The installed pi-ai already ships `providers/google` and `providers/google-vertex`, though Kemiri does not register them today. Registering an approved direct Google API provider reuses the existing agent loop and is less work than an external worker. Do not reuse Kemiri’s OAuth credential plumbing for a CLI session.
- `packages/server/src/runtime.ts` assembles the pi-durable project registry (coding tools, board, codemode, artifacts, memory and other extensions). `workers.ts` launches pi-durable child conversations and associates worker lifecycle, reports, isolation, coordinator handoff and board task tracking with them. The coordinator gets the worker’s final report, not its whole transcript. Task-bound native workers keep `task_progress`; the full board and automatic memory are coordinator features. Use the existing assignment/report/workspace split as a seam for another worker backend, not the provider list as a dropdown that hides two very different runtimes.
- `packages/server/src/mcp.ts` binds imported MCP servers **into** Kemiri as tools, with role/policy checks; it does not export Kemiri’s native registry as an MCP server. See the MCP and request accounting sections in [`../DESIGN.md`](../DESIGN.md) and `request-log.ts`, `cache-retention.ts` and `subscription-usage.ts`. Those pi-ai wrappers and pi-durable hooks do not see underlying CLI requests.

| Option | What stays working | What breaks or needs building | Effort |
| --- | --- | --- | --- |
| **Official CLI as whole worker**, initially headless NDJSON | Native coordinator and its tools/codemode/board/memory/usage stay intact. Kemiri can own task assignment, workspace, lifecycle, final report and selected artifact retention. CLI owns coding tools, local rules and agent session. Stream text/tool progress and optional token counts from documented events. | External worker has no native Kemiri tool calls, codemode, board tools or memory. Pass only selected task context and memory in the brief. Collect declared artifacts in Kemiri after validating paths. No native request trace, context/cache/compaction statistics, subscription windows or exact costs for the worker. Needs worker event/transcript, cancellation, resume and restart mapping. | **Medium** prototype; **larger** for durable queues, audit and recovery. |
| **Shell out per turn as a pi-ai model provider** | On paper the same UI selector and coordinator/worker loop. pi-ai could expose plain text and counters if translated. | Not equivalent to a provider. `agy` executes its own tool loop, changes history and can add subagents. No documented raw model request with Kemiri-native tool calls/IDs and tool-result injection. Text or structured JSON emulation loses reliable tools/codemode/board/memory/artifacts, risks duplicate side effects or prompt duplication, and fabricates per-request usage if mapped naively. Extra process overhead and double context management. | **High, reject.** Use an approved direct model API if Kemiri must own the loop. |
| **ACP client plus a scoped MCP server** | Keep the same whole-worker model. ACP can give structured session/permission/tool events and interactive approval; MCP can let the external agent read its task, update progress and request artifact retention. Native coordinator stays intact. | ACP does not export board tools or vendor-independent billing. Neither protocol recreates native codemode or automatic memory, prompt caching or request traces. Requires ACP client adapter, normalized events and approval/cancel UI, an MCP server and explicit authorization for each exported call. | **Medium–high** for ACP; bridge later, one tool at a time. |

**Bridge direction:** `Kemiri → ACP/headless → official agent`, with `official agent → MCP → narrow Kemiri task service`. A local stdio server or tightly scoped authenticated endpoint can expose `task_read`, task progress and artifact submission; it should resolve project, worker and assigned task from the launch scope, not a model-supplied ID. Validate paths against the worker artifact root, including symlinks. Add only selected read-only tools after review. Do not export arbitrary codemode, shell, credentials, broad board mutation or memory writes. Never pass a full-owner Kemiri session to a subprocess. The reverse (an MCP tool in Kemiri that calls a CLI) is possible to build, but would be text-task delegation, not a model provider or a consumer policy exception. Test MCP auth and permissions independently of model behavior.

**Generic shape:** Give a backend a task brief, workspace, approved auth/billing profile, model hint, permission policy and optional opaque session reference. Return normalized text/progress/tool/result events and optional usage, with clean cancel and explicit failure states. Keep vendor-specific event decoding, model names, permission mapping and auth out of board logic. Example next adapters: [Codex `exec` NDJSON](https://developers.openai.com/codex/noninteractive/) or [Codex App Server](https://developers.openai.com/codex/app-server/); [Claude Code CLI](https://code.claude.com/docs/en/cli-reference) or [Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview), whose docs restrict third-party claude.ai login or rates without approval; [Gemini CLI headless](https://geminicli.com/docs/cli/headless/) on an eligible API/enterprise credential. Verify vendor terms separately and default integrations off. No claims about cross-vendor subscription support follow from a transport working.

## Risks, gates and choices

- **Policy and privacy.** Keep personal subscriptions disabled in bundled integrations unless explicitly approved. Antigravity terms say Google records interactions and can use them for improvement unless that preference is changed. The terms say data is still used to provide the service when telemetry is off. Minimize what leaves the workspace and never send confidential board or memory context without authorization.
- **Login and process lifetime.** An approved deployment should use an isolated service user, stable tool-owned HOME/keyring where needed, a trusted executable and explicit environment instead of inheriting unrelated provider credentials. Keep prompts off process arguments where practical. Redact diagnostics, cap output and disk use, enforce deadlines and terminate the process group. Store opaque session IDs bound to profile, project and workspace, never tokens. If a process dies after side effects, report termination and inspect state before attempting continuation. Do not silently rerun.
- **Quota and spend.** Google ties quota to work/capacity, not a fixed prompt count. Report quota/rate limits separately from auth and tool failures. Start with one worker per profile, no unattended schedules and no automatic credit overage. On a quota error, stop or apply a bounded retry only if documented and safe before side effects. Do not rotate accounts. API/enterprise spend needs an explicit project, limits and Cloud billing review.
- **Usage visibility.** Headless JSON reports input/output/thinking/cache-read/total tokens. NDJSON results in multi-turn mode are cumulative, so baseline and delta them or store final totals, never sum every result; also avoid double-counting step events. Google’s [CLI credit UI](https://antigravity.google/docs/cli/credits/) and `/usage` are plan views, not a reliable machine-readable billing feed. Show wall time, vendor status and attributable tokens where emitted; show currency, quota remaining and missing counters as unknown unless authoritative. Do not backfill pi-ai cost from guessed model rates.

1. **Now — choose policy and billing.** The owner can keep direct `agy` separate and use a Gemini API provider for native Kemiri features, or approve API/Cloud billing for a CLI-worker pilot. If the subscription itself is mandatory, decide whether a separate, directly prompted ACP client is enough and ask Google to confirm that exact scope before enabling it. Do not offer coordinator delegation on consumer login.
2. **First pilot, only on an approved route.** Keep the coordinator native. Implement one opt-in external worker on a disposable workspace with no MCP, plain completion and a bounded output stream. Test a short reply, an allowed action and a denied action, cancellation, bad model, expired/revoked auth, restart/resume, quota failure and usage. Verify artifacts and task outcomes on the Kemiri side. Feature-flag the backend and turn it off on failure; no automatic fallback to subscription.
3. **Then add what the pilot needs.** If users need interactive approvals or live sessions, add ACP. If they need board progress or retained artifacts mid-run, add narrowly scoped MCP. Add further providers only when their documented interfaces and billing terms pass the same gates.

**the owner’s choices:** Is direct subscription use outside Kemiri enough, or is paying for an approved integration acceptable? If integrating, is a separate worker with a report and progress enough, or are native Kemiri tools and memory essential? If the integration must spend a subscription, who will obtain written Google approval for the exact use before enabling it?
